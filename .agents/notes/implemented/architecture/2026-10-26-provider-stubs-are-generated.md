# Agent Note: 被裁剪构建替换的 provider stand-in 由生成器写

Status: implemented

## Problem

`feat(coding-agent,ai): 用 onResolve 替换未选中的组件` 引入了裁剪构建的第二半：
`providerSets` 排除的 catalog shard 在 esbuild 的 `onResolve` 里被替换成
`packages/ai/src/providers/disabled/<provider>-models.ts`。替换点要求 stand-in 的
**导出名**与 shard 一致，`validateStubs` 在 bundle 之前逐对比较，不一致就失败。

shard 是生成的（`generate-models.ts` 写 `src/providers/*.models.ts`，文件被 gitignore），
stand-in 是手写的（48 个进仓，等于 `providerSets.presets` 的成员）。于是：

- models.dev 新增一个 provider，`recordFullProviderSet` 把它写进 `providerSets.all`
  （见 [provider set 记录](../bug-fix/2026-10-26-provider-set-recording-survives-marker-replacement.md)），
  shard 也就生成了；stand-in 没有人补。
- 被裁剪构建真正会替换的 shard，是选中集合之外的那些。`presets` 之外 158 个 shard
  没有 stand-in，但全量 flavor 不替换它们，平时没人踩到。哪天某个 flavor 的集合不含
  `presets` 里的成员，或者选了 `presets` 之外的新 provider，`validateStubs` 立刻抛出
  100 多行 `no src/providers/disabled/xxx-models.ts`，而且没说这是生成器漏写的。
- issue #224 的复现路径：重新克隆后跑 `scripts/build-single-file.mjs`。干净 clone 里
  没有 shard，第一步 `generate:models` 把所有 shard 补上，stand-in 还是仓库里那 48 个。

## Decision

**stand-in 和 shard 由同一次生成写出，两边都进 .gitignore。**
`generate-models.ts` 的 `providerStub(providerId)` 为每个生成的 shard 写
`src/providers/disabled/<artifact>-models.ts`，并删掉没有对应 shard 的孤儿；
`writeEmptyCatalog()`（`--providers __NONE__`）也清空 `disabled/`。两边集合因此
永远相等，`validateStubs` 只剩「导出名漂移」这一个真实风险。

**干净 checkout 从 stand-in 读 provider 名单。** `readProviderModuleIds` 在 shard
不存在时改读 `disabled/`：审计的是「哪些 provider 有 catalog」，stand-in 与 shard
一一对应，所以它不是另一个事实来源，只是同一个集合里留在 checkout 里的那一半。
两个都没有就报「先跑 `pnpm run generate:models`」。`validateStubs` 遇到缺失的 shard
跳过导出名比较（stand-in 的导出名就是 shard 的导出名，生成器保证的）。

**手写的 48 个也归生成器管。** 它们的正文换成与 shard 同义的
「Generated by scripts/generate-models.ts; do not edit」：手工改会在下次生成时被覆盖。
原文里「构建为什么用 alias 而不是运行期过滤」的说明搬到了这里和
`scripts/build-apis.mjs` 的注释里。

代价是生成器要多写 200 来个 20 行的空 catalog，且下次构建会删掉这 48 个旧文件
（它们从 index 里移除，由生成器现场产出）。体积不是问题：stand-in 只在**不含**
该 provider 的构建里被读，全量 flavor 一个字节都不进 bundle。

**顺带修掉一个真实裁剪漏洞**：`resolveModulePath` 处理
`@nanopi/pi-ai/providers/<x>.models` 这种包说明符时只去掉 `.js` 后缀，而包说明符
本来就不带后缀，于是与 map 键（`.../x.models.js` 去掉后缀 = `.../x.models`）对不上。
**全量构建没问题，裁剪构建会保留本该替换掉的 shard**：`base` flavor 因此多带了
~1 MiB provider 数据（单文件 6.4 MiB → 5.4 MiB）。现在两种形态都归一成「去掉 `.js`」。

## Alternatives considered

- **保持手写，把 `validateStubs` 降级成警告**：等于让裁剪构建在导出名漂移时静默
  打包空 catalog，模型查不到却没有任何错误。这正是 `validateStubs` 存在的原因。
- **只给 `presets` 之外的 provider 一次性补齐 158 个 stand-in**：解决今天的失败，
  不解决机制——下次 models.dev 再加 provider，同样的失败重来一次。
- **在 `validateStubs` 里现场生成缺失的占位文件**：把只读的校验变成写盘，构建期间
  改源码树，失败时留下半写状态。生成器是唯一该写这两个目录的地方。
- **让 `readProviderModuleIds` 继续只读 shard，构建脚本保证先生成**：构建脚本确实
  先生成，但 `validateStubs` 也被 `scripts/*.test.mjs` 直接调用，而测试跑在可能是
  干净 checkout 的机器上。

## Consequences

- 新增 provider 只需一次 `pnpm run generate:models`（或任何构建），shard 与 stand-in 同批出现。
- `providerSets` 仍是配置事实：`all`/`presets`/`core` 决定生成哪些 shard，stand-in 只是镜像。
- `validateStubs` 的报错改成一行一个 provider，并在标题里带数量：158 条挤一行读不出来。
- 干净 checkout 上 `node --test scripts/build-apis.test.mjs` 仍能跑，因为它读 stand-in。
- 生成目录被删掉（`git clean -xfd`）后必须先 `pnpm run generate:models`，报错信息直接给这条命令。
