# Agent Note: node 24 is the floor, and the bundled targets follow it

Status: implemented

## Problem

`engines.node` 在 7 个 `package.json` 里都是 `>=22.19.0`（根 + agent / ai /
coding-agent / extra / tui / webui）。issue #307 把「node v24」列为最后一个
待办 major，并把它归到「基础设施」，容易被理解成只改一行版本声明。

实际上 `engines.node` 本身不做任何事：pnpm 10 起 `engineStrict` 默认 false，
`pnpm install --frozen-lockfile` 遇到不匹配只打 warning。真正约束下限的是四处
各自独立的落点：

- 6 个 workflow 的 `actions/setup-node` `node-version`（`ci.yml`、
  `build-binaries.yml` ×3、`issue-analysis.yml`、`npm-audit.yml`），
  决定 CI 在哪个运行时上验证。
- 两个 esbuild `target: "node22.19"`（`scripts/build-coding-agent-bundle.mjs`、
  `scripts/build-coding-agent-single-file.mjs`），决定发布产物的语法级别。
- 根与 5 个子包的 `@types/node`（22.20.5），决定 tsc 能看见哪些运行时 API。
- 文档里的「Node.js 22.19 or newer」（coding-agent 的 README 与 quickstart）。

只改第一处会出现「声明 24、CI 在 22 上跑、产物降级到 22 语法、类型库还是 22」
的组合——每一项单独看都不报错，合起来就是一整套没验证过的声明。

## Decision

下限提到 `>=24.0.0`，四处一起改：

- 7 个 `package.json` 的 `engines.node` → `>=24.0.0`。
- 6 个 `actions/setup-node` 的 `node-version` → `24`（`build-binaries.yml`
  里三处写的是 `'24'`，与文件原有的引号风格保持一致）。这几处
  `setup-node` 是 v7.0.0，运行时不支持 node 24 的问题不存在。
- esbuild `target: "node22.19"` → `"node24"`。这是唯一真正决定产物语法级别的
  开关；不改就只是白白丢掉 24 的语法收益，并让产物和声明对不上。
- `@types/node` 22.20.5 → **24.19.2**，root + agent / ai / coding-agent / extra /
  webui 六处同步（`packages/tui` 不直接声明）。24.19.2 是 24.x 线当前的最高
  patch。
- 文档与 `scripts/build-coding-agent-single-file.mjs` 文件头的注释一起改成
  「Node.js 24 or newer」。

`Dockerfile` 已经是 `node:24-bookworm-slim`，不动。

## Alternatives considered

- **`@types/node` 直接跟到 latest（26.6.5）**：类型库只能比运行时新不能旧是
  对的，但 26 的类型会把 `engines.node` 声明之外的 API 放进 tsc 的视野——代码
  能编过、在声明的 24 上却跑不了。跟 major 对齐（24.x），留 patch 随 renovate 走。
- **只改 `engines.node`，CI 与 esbuild target 留着**：pnpm/npm 都不强拦，看起来
  「也能跑」，但 CI 就变成在 22 上验证一个声明 24 的项目，等于这批升级没有
  任何一处被真正验过。
- **`engines.node` 写 `>=24.19.0` 对齐 `@types/node`**：`@types/node` 只能比
  `engines.node` 老，不能比它新。`>=24.0.0` + 24.19.2 的类型意味着一个不小心就能
  用上 24.19 才有的 API 而 CI 全绿；对齐到 patch 能把这层靠 review 的约束写进
  安装期检查。放弃了：24.x 线上每个 patch 都要跟着改下限，而这些新 API 很少。
- **把 workflow 的 `node-version` 改成 `24.x`**：`setup-node` 两种写法都接受，
  但仓库现有 6 处全是裸 major，跟着写 `24`。

## Consequences

- 22.x 不再受支持。实际拦截仍然只是 warning（`engineStrict` 未开），所以这条
  承诺靠文档和 CI 维持，不靠安装期报错。
- `install.js` 那一行 `curl ... | node` 现在要求本机已有 node 24；没有更早的
  检查点，行为与之前一致（缺 node 就是 `command not found`）。
- 验证面：`pnpm install --frozen-lockfile --ignore-scripts`、`pnpm run build`、
  `pnpm run check`、`node ./test.mjs`、`packages/tui` 的 `node --test`、
  webui 的 `typecheck` 与 `next build` 全部在本机的 node 上跑过一遍。
  `@types/node` 24 升上来后 tsc 不再报 `sidecars.ts` 的 `ReadableStream` 方差
  错误——那条在 22 的类型下是既有报错，24 的 lib 定义把它消掉了。
- 剩余 major 清单只剩 `protobufjs` v8（等 `@google/genai` 放行），见
  [runtime major bumps](./2026-10-27-runtime-major-bumps.md)。
