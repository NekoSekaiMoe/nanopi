# Agent Note: EOS-only 空补全标成可重试错误，复用整轮重放

Status: implemented

## Problem

`shinytale/nanopi#580` 第 4 条：OpenAI-compatible 后端偶发只回一个
`finish_reason: "stop"` 的 chunk，没有 `delta`、没有内容块、`usage.output` 为 0。
`openai-completions.ts` 的完成判定只把「缺 `finish_reason`」当异常，于是这轮流成
`stopReason: "stop"` 的正常成功，agent loop 收工，用户看到一轮什么都没发生。
`agent-session.ts` 也没有空 turn 检查。

omp 用 `withReplaySafeStreamRetry` 在流层内部对这种 EOS-only 空补全重试最多 2 次。

## Decision

空补全在流结束判定处抛错，转成 `stopReason: "error"` +
`errorMessage: "Provider returned an empty completion (EOS-only)"`；`retry.ts` 的
`RETRYABLE_PROVIDER_ERROR_PATTERN` 加 `"empty completion"` 让它命中分类器。

判定条件三条同时成立才触发：`stopReason === "stop"`、`content.length === 0`、
`usage.output === 0`。带 usage 的空响应（output 为 0 但模型确实没生成）和无 usage 的
流式响应都满足第三条，但前两条保证只有真正零内容的一轮被标错；带文本的正常 stop、
带 toolCall 的 `toolUse` 都不受影响。

重试**不**在流层做。转成 error 后由 nanopi 已有的两条链路接住：coding-agent 的
`_prepareRetry` / `_omitRecoveryAttempt`（整轮重放）和 SDK 的 `retryAssistantCall`。
错误信息不命中 `isContextOverflow`，所以不会被 compaction 抢占。

## Alternatives considered

- **照搬 omp 的 `withReplaySafeStreamRetry`，在流层内部重试 2 次。** 最强理由：对上层
  完全透明，`completeSimple()` 直接拿到第二次的结果，不需要上层理解这种错误。否决理由：
  [不换 edit 的 wire 契约，也不做流中打断](../../rejected/feature/2026-11-07-omp-edit-and-stream-rewrites.md)
  已定「流式层保持整轮重放」。流层重试要求缓冲已发事件、或保证 `start` 之前重试，否则
  已推给 TUI 的 `text_start` 等事件会重复；`AssistantMessageEventStream` 的 `push` 在
  `done`/`error` 后置 `done`，一个流实例无法发两次终止事件。要透明重试得重写流层，
  代价远超一条判定。
- **在 `agent-session.ts` 加空 turn 检查（`stopReason === "stop" && content 为空`）。**
  能补上 coding-agent 这一条路径，但 `completeSimple()`、SDK 直调、compaction/分支摘要
  这些调用方拿不到检查，且要把「空」的判定散到两处。在 adapter 边界标错是单一事实来源。
- **把 `finish_reason: "stop"` 但无内容直接当成功（不改）。** 这正是 #580 报告的现象：
  一轮静默空转，用户以为模型没响应。保留等于不修。

## Consequences

- 持续返回 EOS-only 的后端不再静默空转：默认 `retry.enabled: true`、
  `baseDelayMs: 15000` 下最多重放 3 次（15s/30s/60s，见
  [agent 级重试默认退避](2026-11-07-agent-retry-backoff-default.md)），仍失败则把
  `empty completion` 错误显示给用户。重试的是整轮请求，不是流内续跑。
- `packages/ai/test/openai-completions-raw-stop-reason.test.ts` 原来用「裸 stop chunk」
  当「成功 stop」的 fixture，正是这次要修的形态；改成先发一个带文本的 chunk 再 stop。
  其他用裸 stop chunk 做 fixture 的测试只断言 payload/params，不断言 `stopReason`，
  所以不受影响。
- `retry.ts` 的 `"empty completion"` 是宽松子串：别的后端若在错误信息里写
  「empty completion」也会被当作可重试。当前没有这类已知文案；真出现语义冲突时再收窄。
- 覆盖：`openai-completions-empty-completion.test.ts` 断言空补全转 error 且可重试、
  正常带文本的 stop 仍是成功；`retry.test.ts` 断言分类器命中。
