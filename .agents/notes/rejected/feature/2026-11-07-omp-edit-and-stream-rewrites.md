# Agent Note: 不换 edit 的 wire 契约，也不做流中打断

Status: rejected — 用户判断：hashline 编辑和 TTSR（流中正则命中即打断）都能省 token，但要换 `edit` 的 线上契约、重做流式层，代价落在「全部模型的兼容性」上。不做。见 shinytale/nanopi#574。

## Problem

omp 有两处改的是 wire 契约而不是实现，收益写得很硬：

- **hashline 编辑。** 模型不改「原文本 → 新文本」，而是给 `[PATH#TAG]` + 行号 + 内容哈希锚点，
  然后只说改成什么。锚点对不上就整块拒绝，不会写坏文件。README 给了数字：Grok 4 Fast 同一任务
  输出 token 少 61%。
- **TTSR。** 正则命中流中的 token 就中断、注入规则、从断点续跑。它的实现面是
  `ttsr-coordinator` + `ttsr-outputs` + 三份 interrupt/warning/tool-reminder prompt 模板。

nanopi 这一侧的相关形状：

- `edit` 是精确文本替换，`edits[].oldText` 必须唯一命中（`packages/coding-agent/src/core/tools/edit.ts:24,147`）；
  匹配走精确优先、失败再模糊（`edit-diff.ts:207` 起，`normalizeForFuzzyMatch` 在 `:34`）；命中多处时
  直接报错并列出坐标（`edit-diff.ts:374-378`）。
- 陈旧读取靠 `read-snapshot.ts`（45 行）在 `edit` 结果里加一句提示，**不阻断**写入。文件开头就写着
  理由：挡住正确工作的警告比它防止的陈旧读更贵。
- 重试是整轮重放：`_prepareRetry`（`agent-session.ts:4616`）退避后 `_omitRecoveryAttempt`（`:1646`）
  把失败那轮从模型投影里摘掉，再重新发一次请求。

## Proposal

两条都不做：`edit` 继续精确文本替换，流式层继续整轮重放。

## 为什么不换 hashline

换它是一次全身手术，牵四处：

1. `edit-diff.ts`（672 行）的 fuzzy 匹配、BOM 剥离、`oldText` 唯一性检查全部要重写成锚点校验；
2. `read-snapshot.ts` 那套「读了没有、之后变没变」的 advisory 检查失去意义，因为锚点自带版本；
3. 工具声明与 `promptGuidelines` 要重写——它受 5k token 预算管着
   （[prompt-budget-5k](../../implemented/simplification/2026-10-27-prompt-budget-5k.md)）；
4. 所有测试、`docs/`、以及模型侧的行为都要跟着变。

而 nanopi 现在的等效收益已经在别处兑现：`read` 给 `offset=N to continue` 的续读坐标
（`packages/coding-agent/src/core/tools/read.ts:226-235`），`edit` 报错时直接告诉模型「Found N occurrences，
把上下行加进 oldText」——这是可执行的纠正，不需要模型理解哈希。

真正的问题是：收益（token）归所有模型，代价（兼容性）也归所有模型。omp 敢换是因为它自己就是
harness 作者，模型侧的 template 也自己维护；nanopi 只走结构化 `tool_calls`，一旦锚点格式被模型读歪，
退路只有靠错误信息把它拽回来。

## 为什么不引 TTSR

它要求「在 token 中间打断并从该点恢复」，而 nanopi 的重试是整轮重放：失败轮从投影里摘掉，再发一次。
要做 TTSR 等于重做流式层——拿到流的中间态、保留已产出内容、在注入规则后从同一位置续跑。

其次，它的复杂度成本直接撞 5k 预算：规则要么常驻（占 system prompt），要么按需（进 tool prompt 时
又要判「什么时候该在」）。omp 为此写了三份专用 prompt 模板和一套生命周期文档（309 行）；
这套东西在 nanopi 里的对标物是一句话就能说完的重放策略。

## Alternatives considered

### 只做 hashline 的「拒绝坏补丁」那半

最强理由：真正贵的不是 token，是「模型写坏文件之后的一轮修复」。锚点校验能拒绝陈旧补丁，
`read-snapshot.ts` 现在只提示、不阻断，两者看似互补。

否决理由：`read-snapshot.ts` 的不阻断是有意的（见文件开头注释）——挡住正确工作比防住陈旧读更贵。
要阻断得先证明「陈旧读导致写坏」在 nanopi 上真实发生过，目前只有一次理论推导。

### 只做 TTSR 的「命中即提示」那半（不打断流）

最强理由：不动流式层，只在流结束后把命中规则的提醒插进下一轮，成本极低。

否决理由：那已经不是 TTSR 了，是「后置提醒」，nanopi 的等价物是 `promptGuidelines` 与 AGENTS.md。
真需要按内容动态提醒，先有具体规则再谈，不要先造机制。

## Consequences

- `edit` 的失败信息与 `read` 的续读提示是这条路的承重墙。以后要改它们，理由得是「模型被喂错事实」，
  不能是「换个更省 token 的格式」。
- 如果哪天真的换 `edit` 契约，四处手术的清单在上面「为什么不换 hashline」里，照它估工。
- 流式层保持整轮重放，这条与 429 退避时长是两件事：退避算错要修（`retryDelayMs` 不看服务端 hint），
  重放机制本身不改。
