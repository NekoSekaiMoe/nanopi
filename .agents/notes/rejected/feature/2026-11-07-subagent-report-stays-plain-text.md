# Agent Note: 子代理报告维持纯文本，不换 schema 校验对象

Status: rejected — 用户判断：现阶段不改。子代理只回最后一轮 assistant 文本这件事没有造成实际损失， 换结构化报告要先定义 schema、再定校验失败时怎么办。见 shinytale/nanopi#574。

## Problem

`pi-subagent-mini` 的回传路径是：子进程把每轮消息以 NDJSON 打到 stdout，父进程只留最后一轮的
assistant 文本（`packages/coding-agent/src/extras/pi-subagent-mini/src/index.ts:638` 的 `lastAssistant`），
job 结束时写进 `finalOutput`（`:661`），失败信息走 `errorMessage`（`:778`）。

所以父会话拿到的是「一段话」，不是「符合某个 schema 的对象」。omp 那侧有子代理带回结构化对象的做法，
看起来是「契约更严」。

## Proposal

不改。子代理继续回纯文本 + 状态 + usage。

## 为什么不改

先看这条路的替代品已经存在：[in-process subagent sessions](../simplification/2026-10-22-in-process-subagent-sessions.md)
的备选方案里写过「结构化回传」这条路，并明确没否掉它，理由也不是「省内存」而是「报告契约更结构化、
消掉 NDJSON 与进程树 kill 三个包袱」。也就是说这个方向是被认可的，只是当时没有需求。

现在仍然没有需求，而这个改动的前置条件有两个都不轻：

1. **schema 谁定。** 子代理任务是自由文本 prompt（`launch(job, prompt, ...)`），没有「任务类型」这个概念。
   要校验就得先让调用方声明期望形状，等于给 `subagent` 工具加一个必填字段，而它现在是「扔一句话进去」。
2. **校验失败怎么办。** 纯文本永远不会「不合 schema」，最坏是答非所问，模型自己会重问。
   换成 schema 之后要定义：重试一次？还是把校验错误回给子代理让它重答？那笔预算现在花在别处。

代价也不只是这两件事：`finalOutput` 现在被 `report`、`dependency`、`withWorktreeReport`、截断
（`MAX_REPORT_CHARS`）四处消费，至少四条路径要跟着理解「报告有两种形状」。

## Alternatives considered

### 结构化成「自由 JSON + 可选 schema」

最强理由：不强制声明 schema 时行为不变，只在需要时收紧，兼容现有所有调用。

否决理由：这正是「没有痒点先造机制」。真出现「父会话反复读错子代理报告」的证据，再按那次证据
定 schema 形状，比先造一个可选壳子直接。

### 只在报告尾附一段结构化摘要（不替换正文）

最强理由：正文照旧，另加一个 `{ status, filesChanged, nextStep }` 之类的固定小对象，成本比分模块
schema 低得多。

否决理由：`finalOutput` 已经是「最后一条 assistant 文本」，附摘要等于让模型多写一段它本来可以写进正文
的话。真需要这几个字段，先在子代理的 prompt 里要求它写进正文，看有没有用。

## Consequences

- 与 [in-process subagent sessions](../simplification/2026-10-22-in-process-subagent-sessions.md) 的结论
  一致：那条备选方案仍然「可以做但没做」，这篇只是把「现在不做」写实。
- 重开条件：出现「同一个子代理任务反复被父会话误读报告」的实例。届时的落点是在 `subagent` 工具上
  加可选 schema，不是重做 NDJSON 通道。
