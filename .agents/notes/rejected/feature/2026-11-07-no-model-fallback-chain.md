# Agent Note: 不做 model role / fallback chain，也不把多凭据轮换上升为核心能力

Status: rejected — 用户判断：现阶段不做。两者都是「一个 provider 饱和就绕到下一个」的旋钮， nanopi 的定位是个人工具，模型切换的成本由人来做，不需要核心层长出一套路由。

## Problem

#574 对照 omp 时带出两件事：

- **九个 model role + `retry.fallbackChains`。** `default`/`smol`/`slow`/`plan`/`vision`/`advisor` 等按意图
  路由到不同模型；fallback chain 在主模型 429 或撞 quota 时让下一项接手本轮，冷却后恢复。
- **同 provider 多凭据轮换。** 多个 API key 叠在一起，运行时按 session affinity 轮换，每个凭据独立退避。

nanopi 的现状：

- settings 里没有 role 和 fallback 的概念；`_modelFallbackMessage`
  （`packages/coding-agent/src/core/agent-session-runtime.ts:81`）名字像 fallback，实际是「恢复会话模型失败」
  的提示文案。
- 凭据是 per-provider 单条：`packages/ai/src/auth/types.ts:52` 明写 "one credential per provider"，
  `modify` 是唯一写路径，用于串行化读改写与 OAuth 刷新。
- 但**基础设施是现成的**：`packages/coding-agent/src/core/virtual-models.ts`（257 行）就是
  「请求级路由到物理模型」的层，`_getSummarizationRequestAuth`
  （`packages/coding-agent/src/core/agent-session.ts:720`）已经用它给 compaction 选模型。
- 多凭据轮换在 nanopi 里有先例，但是**按模块做的**：`packages/coding-agent/src/extras/websearch/src/engines.ts:10-12`
  写着「一个引擎的 N 个 key 先试 N 次再换引擎，只有 auth / rate-limit / quota 失败才烧 key，
  500 和网络错误直接换下一个引擎」。

## Proposal

两件都不做：不引入 role/fallback chain，不把多凭据轮换做成核心层能力。

## 为什么不引 role / fallback chain

role 是给「同时跑很多 provider 的工作室」用的：`smol` 做廉价的子代理分发，`vision` 做看图，`advisor` 挂一个
审稿模型逐轮注入意见。nanopi 的用户是自己一个人，切模型是 `/model` 一次动作，成本极低，
不需要系统替他决定「这一轮该用哪个」。

fallback chain 的前提是「同一个模型反复饱和，换一个就能过」。这个前提在 #574 里只出现过一次
（一个 NPC 撞上 429 `code:14003`），而且那次的直接原因是退避窗口比服务端要求的 30 秒还短，
不是「这个模型彻底不可用」。那个原因已经被默认退避 15s/30s/60s 覆盖掉了（见下），
所以更不构成加 fallback 的理由。等它作为**模式**再发生第二次，再谈。

真要做的话，底子已经有了：挂在 virtual model 上比新造一套 role 系统省事得多。这条记在这里是为了
下次不要把「加个 role 字段」当新想法重新推一遍。

## 为什么不把多凭据轮换上升为核心能力

`AuthStorage` 的「per-provider 一条凭据 + 单一写路径」是一条有意的约束：它让 OAuth 刷新是
串行读改写，并发请求不会双重刷新同一个 token（见 `packages/ai/src/auth/types.ts:51-58` 的注释）。
把「一个 provider N 条凭据」塞进这层，等于在凭据解析处引入轮换状态与 per-credential 退避，
核心每一条取 auth 的路径都要考虑「这次轮到哪个」。

而 websearch 那次做轮换，需求是具体的：一个引擎一个 key，key 烧完就得换，且「500 不代表 key 有问题」
这条判断只在那个模块的语义里成立（`packages/ai/src/utils/provider-retry.ts:53-70` 也有类似的服务端
hint 校验，但它是 provider 级的，与「哪个 key 该退休」是两码事）。结论留在备注里：
**这类能力按模块需要做，不进核心层。**

## Alternatives considered

### 只做 fallback chain，不做 role

最强理由：role 是给多模型工作流用的，fallback 是纯粹的容错——两者可以拆开，后者对单人用户也有意义。

否决理由：拆开之后它仍然要回答「换到哪个模型」，而 nanopi 现在连「首选模型集合」这个概念都没有；
先有为「首选 + 备选」定义语义的需求，再谈机制。真要应急，`retry.nonRetryableErrorPatterns`
（`packages/coding-agent/docs/settings.md:124`）已经能让人把某个网关的假 429 从「重试」翻成「立刻失败」，
比 fallback chain 便宜。

### 三处统一做多凭据轮换（核心 + websearch + 子代理）

最强理由：统一一处实现，省掉重复逻辑。

否决理由：websearch 的轮换语义是「换引擎」＋「换 key」两层，核心的凭据存储是「一个 provider 一条」，
两者的失败语义不同——强行统一要在一层里表达两套「什么错误该丢弃什么」。保留各自的实现，
把「500 不代表凭据有问题」这条判断写在这里，比抽一个共用抽象更省事。

## Consequences

- 模型饱和时 nanopi 的应对是「重试 + 告诉用户换模型」。该提示已经存在
  （`packages/ai/src/utils/retry.ts` 的非重试分类覆盖 quota/billing）。
- 429 退避时长不看服务端 `retry_after` 这件事已经在别处处理了一半：默认值从 2s 抬到 15s，
  三次退避变成 15s/30s/60s（[agent 级重试默认退避](../../implemented/bug-fix/2026-11-07-agent-retry-backoff-default.md)）。
  `retryDelayMs`（`packages/ai/src/utils/retry.ts:181`）仍不读服务端 hint，那要动 `AssistantMessage`
  的公开字段。它不在这篇的范围里，修它是改算法，不是加 fallback。
- 下次有人提 role/fallback 时，先问两件事：模型集合的语义有了吗？「反复饱和且换模型就过」发生了
  第二次吗？都没有就引到这篇。
