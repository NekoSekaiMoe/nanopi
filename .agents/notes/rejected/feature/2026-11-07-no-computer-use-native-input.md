# Agent Note: 不做 computer use 工具与 native 采集层，GUI 驱动留在 bash + read 的流程里

Status: rejected — 用户判断：先记下现状，不做。采集和注入都能用 CLI 走 `bash`，`.node` 只赢在没有外部依赖那点延迟，却要背 Wayland 断头、六份手工 prebuild、以及一整套沙箱与权限模型的重写。见 shinytale/nanopi#577。

## Problem

#577 问的是「nanopi 有必要引入 computer use 吗」，并明确排除了 nut.js，指的是编译成 `.node` 的原生采集/注入。

这个问题不是空想：仓库里已经有一个成熟的 native 先例（`packages/tui/native/`，一个 `.node`、六份 prebuild，剪贴板加修饰键），图那一侧也已通（`ImageContent` 在 `packages/ai/src/types.ts:440`，`read` 在 `packages/coding-agent/src/core/tools/read.ts:179` 就发图，`agent-session.ts:870` 统一过 photon 缩放）。缺的只有采集与注入。

于是「要不要顺着这个先例再加一个 `.node`」看起来是自然延伸。这篇要回答的正是：延伸出去要付什么，付得起吗。

## Proposal

不引入 computer use：既不做注入型原生工具，也不做只读截屏工具。GUI 驱动以流程形态存在——抓图走平台 CLI（`screencapture -x` / `import -window root` / `grim` / PowerShell 抓屏），看图用 `read`，点击键盘用 `bash` 起 `xdotool` / `ydotool` / `wtype` / `cliclick`。

这条路的两个好处不是「便宜」，而是**它复用了已经存在的两个契约**：`bash` 已经在 `GATED_TOOL_NAMES`（`packages/extra/src/extension.ts:51`）和 `SHELL_TOOL_NAMES`（`packages/extra/src/sandbox.ts:28`）里，`read` 已经在发 `ImageContent`。新增工具等于给这两处各开一个新口子，流程形态一个口子都不开。

## 为什么 native 采集换不到东西

`packages/tui/native/` 能保持这么小（六份 prebuild 加起来 156K），是因为它的职责被剪到只剩剪贴板和修饰键。图那一侧不是「再加一个导出」的量级：

**Linux 只有一半能用。** X11 下 `xcb_get_image` 截图、XTEST 注入都成立，编译单元只需在现有 `-nostdlib -lxcb`（`packages/tui/native/build-native.mjs`）上多写几十行。Wayland 下截图走 xdg-desktop-portal + PipeWire、注入走 libei/RemoteDesktop 门户，那是 D-Bus 加独立进程的活，塞不进 `-nostdlib` 单单元。而主流发行版都在往 Wayland 走，于是「native 省掉外部依赖」这个唯一优势在最常见的场景下直接归零——真要覆盖还是得回落 `grim` 和 `ydotool`。

**darwin/win32 补得上，但贵在授权不在编译。** `SendInput` 在已链的 `user32`，`CGWindowListCreateImage` 在已链的 `CoreGraphics`；真要 ScreenCaptureKit（macOS 12.3+）就得把现在的部署目标 `arm64-apple-macos11.0` / `x86_64-apple-macos10.15`（`build-native.mjs:163`）抬上去，再补 gdi32 之类的链接项。真正卡人的是 TCC：合成事件要 Accessibility、抓屏要 Screen Recording，授权落在宿主终端上，普通用户第一步就过不去。

**六份 prebuild 只能手工出。** `packages/tui/native/README.md` 的 Provenance 明写 CI 从不编译（单个 runner 出不了六个平台/架构组合），prebuild 提交进仓库并在提交信息里记编译器版本与 sha256。增加一个 `.node` 就等于把这套手工流程再走一遍，且每次改 C 源码都要重新出六份。

对照 [不把原生层链进进程](../architecture/2026-11-07-no-native-runtime-from-omp.md) 的结论：那篇否的是「为省一次 `spawn` 引 80k 行 Rust」，这篇否的是「为省一次 `spawn` 多背一个手工 prebuild 矩阵」。同一条预算逻辑，量级更小，方向一致。

## 和现有设计的冲突

这两处冲突比「值不值」更硬：

- **沙箱语义作废。** bwrap 只 ro-bind `READ_ONLY_DIRS`（`packages/extra/src/sandbox.ts:115`）加 cwd/home，没有 `/tmp/.X11-unix`、没有 `$XDG_RUNTIME_DIR`、没有 `/dev/dri`；macOS 的 Seatbelt profile 也碰不到 WindowServer。能点鼠标键盘之后，模型绕过的不是某条命令，而是整个沙箱。反过来说，只读截屏也要先给沙箱补 bind，而这个补丁不该悄悄做。
- **权限模型不适用。** `GATED_TOOL_NAMES` 是 per-call 提示。一次任务几十次坐标点击不可能逐次确认，而「确认一次」等于把整个桌面交出去。plan mode 的 `PLAN_ALLOWED_TOOLS`、hazard 分类也都要各长一维。

## Alternatives considered

### 做只读截屏 module（不进 `tools/*` 内建，默认关闭）

最强理由：注入才是 TCC、沙箱、权限三件事的引爆点，只做截图就把风险面砍到最小；返回 `ImageContent` 给主会话，`normalizeToolResultImages` 那一层已经能接住任意工具产出的图（`packages/coding-agent/src/utils/tool-result-images.ts` 的注释点名了 "screenshot tools"）。

否决理由：它省不掉任何冲突——沙箱要补 bind、宿主要装 CLI、token 成本照付；同时它在功能上和 `bash` 抓图 + `read` 看图完全重复。真需求出现时再按那次需求定形状（谁调、怎么限流、怎么提示成本），比现在造一个默认关闭的模块直接。这是**顺序**上的否决，不是能力上的否决。

### 走 MCP 桌面服务器

最强理由：零代码，第三方生态已有截图/点击服务器，模型侧只要连上就能用。

否决理由：图片在那条路上过不去，两层都断。`mcp-lite` 的结果类型只有文本（`packages/coding-agent/src/extras/mcp-lite/src/client.ts:26`），`textOf` 只留 `type === "text"`（同目录 `src/index.ts:67`）；就算修了，`mcp` 工具把调用扔进子代理，子代理报告是纯文本（`pi-subagent-mini/src/index.ts:661` 只取最后一轮 assistant 文本），而「报告保持纯文本」是已落地的决定，见 [子代理报告维持纯文本](./2026-11-07-subagent-report-stays-plain-text.md)。任何第三方桌面 MCP 服务器带回来的截图都会在子代理那一跳消失。

### 引 nut.js 这类现成库，自己不做原生层

最强理由：跨平台采集与注入它都已经做完了（各平台 prebuild 自带），API 也稳定，比自己写一个 `.node` 少走一遍弯路的可能性很大。

否决理由：它把 prebuild 矩阵从我们的构建链里挪走，却没挪走维护面——依赖里多一棵原生包树，平台/架构覆盖与 Node ABI 跟着它的发版节奏走，而我们今天连侧车那 0.9 MiB 都要权衡（[sidecars 不再内嵌](../../implemented/process/2026-11-06-sidecars-download-in-full.md)）。更关键的是它一点没解决真问题：TCC 授权、沙箱 bind、`GATED_TOOL_NAMES` 的 per-call 语义都不因换了库而改变，而截图产物仍要走我们自己的 `ImageContent` 通道。用一个新依赖换来「同样绕不开的三件事」，不划算。

### 先只写一份 prompt/skill，等真需求再谈工具

最强理由：零代码、随时可回退，缺的只是「模型知道该这么干」——那是 prompt 不是代码。

否决理由：这不是被否的选项，它就是 Proposal，所以不构成取舍。补一句边界说明为什么连这份 skill 也不急着落盘：`bash` 与 `read` 已经是模型手上的工具，缺的只是它自己想到把两者连起来；那是遇到真任务时由提示词补的，不是提前落盘的资产。

## Consequences

- 收益：`GATED_TOOL_NAMES`、`SHELL_TOOL_NAMES`、沙箱 bind 清单、plan mode 白名单、hazard 分类都不新增维度；`packages/tui/native/` 的维护面停在剪贴板 + 修饰键。
- 代价：「这些 CLI 没装」的场景没有兜底，模型只能退回 shell 里的报错自己找替代品。这是自觉接受的缺口——判据是「先有证据，再造机制」。
- 成本仍然是成本，换形态不换量级：一张 1280x800 截图约 1.4k tokens 量级（按面积估算，随模型分块规则浮动）；「截图-点击-再截图」十几步就是几万 token，而失败重试的步数不可控。走 `bash` + `read` 时这笔账一样要付，只是它现在落在模型的选择里，不在工具设计里。
- 重开条件（任一成立就回到这篇）：出现「只能用 GUI、既无 CLI 也无 API」的实际任务，且能用一句话说清是哪个程序；或者 Wayland 侧出现稳定的、不需要额外守护进程的截图/注入入口。届时的第一条路是**只读截屏 module + shell out**，不是 `native/`。
- 与 [桌面壳搁置](../architecture/2026-10-27-desktop-shell-webview-engine.md) 无关但相邻：那篇否的是壳与渲染引擎，这篇否的是桌面驱动能力。两者都会被「维护者自己用不到」同一条理由推着走。
