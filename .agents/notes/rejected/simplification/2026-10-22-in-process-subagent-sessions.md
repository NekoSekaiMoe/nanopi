# Agent Note: 把 subagent 子会话搬进父进程，换不来内存下降

Status: rejected — 实测父进程内多挂一份会话状态只要 ~1 MiB 匿名内存，而「同进程」必须放弃进程隔离（kill 一起收掉子代理拉起的 dev server、子会话独立权限、一个子代理爆掉只死一个 job）；省不下内存，却要付整套隔离重建的代价。不做。见 ISSUE #161 与 [子进程启动方式](../../implemented/bug-fix/2026-10-16-subagent-child-process-launch.md)。

## Problem

`pi-subagent-mini` 的每个子代理是一个独立的 node 进程（`packages/coding-agent/src/extras/pi-subagent-mini/src/index.ts` 的 `resolveChildCommand` + `launch` 里的 `spawn`）。#161 里提出的疑问是：既然每个子进程都要背一整个 node 运行时，能不能把子会话改成进程内，像 peri 那样「一个进程 = 主 Agent + 进程内 SubAgent」，把内存从「按进程数乘」变成「在父进程上叠会话数据」？

这个提案要成立，必须先证明省下的内存是真的。省不出来，剩下的就只有代价。

## Proposal（被否决的原方案，保留以便对照）

`subagent` 不再 spawn，改用 `createAgentSession` 在父进程内建一份子会话：

```ts
const sessionManager = SessionManager.inMemory(jobCwd); // 不落盘的子会话
const { session } = await createAgentSession({
  cwd: jobCwd,
  model: ctx.model,
  sessionManager,
  tools: tools.split(","),
  resourceLoader: sharedLoader, // 关键：复用父会话的模块注册表
});
await session.prompt(task);
```

配套要重做的五件事，全都来自「现在只有子进程能给」：

- 取回：读子进程 stdout 的 NDJSON（`message_end` 里最后一条 assistant 文本）改成监听 `AgentSession` 事件拿最终消息。
- 止损：`detached: true` + `killProcessTree(pid)`（连子代理起的 dev server 一起收）改成 `session.dispose()` + abort，后者只停这个会话自己的工具调用。
- 失败判定：退出码 + `stopReason` 改成只看 `stopReason`。
- 隔离：`env` / `cwd` / `-t` / `--modules` / `--model` 每子一份，改成每会话一份选项。
- 权限：现在子进程是一份普通 nanopi 会话，走它自己的设置；同进程只能共享父会话钩子，或者用 `ctx.executeTool` 手工重跑一遍 `tool_call` 处理器。

## Alternatives considered

### 只改最贵的那件：让子进程少背东西

子进程现在加载「父进程的模块表减去 `CHILD_MODULE_SKIP`」。减法是现成旋钮，一个 `--modules` 就能把子代理压到最小集合。

最强理由是不碰任何隔离，代价只是子代理少几个工具。

否决理由不是「不够优雅」，而是省下的绝对值太小：一个 node 进程的地板就有 45 MiB，这层模块加载实测只值 29 MiB 左右（见下表）。为 29 MiB 维护两套模块表不划算；而要把 45 MiB 地板也省掉，就只能选本 note 否掉的那条路。

### 结构化回传：进程内只读侦察兵，写文件仍走子进程

`mcp` 壳工具（[MCP discovery 与 mcp 壳工具](../../implemented/architecture/2026-10-21-mcp-discovery-and-wrapper-tool.md)）已经是「进程内跑一次工具调用」的先例。扩成只读侦察兵——`read` / `grep` / `find` / `ls` 当函数调用，中间结果不进父 transcript，只回一份报告——能省掉「子代理的工具结果对象堆在父堆里」这一块。

最强理由是省得干净且不放弃进程隔离：写文件和跑 `bash` 的子代理继续留在进程外。

这条没有被否决，只是不能冒充内存修复：省掉的是会话数据那份差额，实测 ~1 MiB/会话（下表）。要做的话，理由是「报告契约更结构化、消掉 NDJSON 与进程树 kill 三个包袱」，不是「省内存」。

### 把子会话做成 `worker_thread`

「独立 V8 isolate + 同进程」听着两全。实测否决：每个 worker 都要重新编译并装载一遍模块（实测 1000 个模块 ≈ 45 MiB/worker），比共享父进程已加载模块的进程内方案贵得多，也不比子进程便宜。而且 worker 与主线程共享同一份进程 RSS 上限，OOM 时一样全体阵亡。

## 为什么不做（实测依据）

所以 #161 里那句「内存 ≈ 进程数 × 单进程 RSS」我在这条讨论里已经撤回：它把可共享的文件页当成了每进程独占。下面这张表是替代它的一版。

本机 Linux / Node 24.22.1，采 `/proc/<pid>/status` 的 `VmRSS` / `RssAnon` / `RssFile`，进程起来 1 秒后采样以排除启动瞬态。样本：1000 个小模块（≈1 MiB 代码）、每份会话状态 1800 条消息（≈1.5 MiB JSON）。

| 场景 | RSS | RssFile（可共享） | RssAnon（独占） |
| --- | --- | --- | --- |
| 裸 `node` | 45.5 | 35.2 | 10.3 |
| 再加 1000 个模块（≈1 MiB 代码） | 74.3 | 44.7 | 29.7 |
| 再加 4 份会话状态（各 ≈1.5 MiB） | 78.2 | 44.5 | 33.6 |

三条结论：

1. 父进程内多挂一份会话状态 ≈ 1 MiB 匿名内存（4 份只多 4.6 MiB RSS / 3.9 MiB anon）。这是本提案唯一能省的东西，也就是全部收益。
2. 子进程的 45 MiB 里 35 MiB 是文件映射（node 二进制 + libc），内核跨进程只留一份物理页；独占部分（`RssAnon`）只有 10 MiB。所以「每个子进程 45 MiB」这个加法是虚的：4 个空转子进程 RSS 简单相加是 188 MiB，其中 144 MiB 是同一批可共享页。
3. 真正按人头算的是模块加载：1000 个模块在进程内值 +29 MiB 独占内存，换成 4 个子进程就等于把这份加载复制 5 份。而这只在共享已加载模块时才能消掉——那正好是要么改子进程模块表、要么同进程。

拼起来：本提案能省 4 MiB，代价是放弃进程隔离；它真能省的 100+ MiB 模块加载，要用别的方式拿到，而那些方式不必破坏隔离。

### 「那就同进程但共享模块，两全」

`createAgentSession` 传 `resourceLoader` 就能复用父会话已加载的模块（`reload()` 对已加载的 loader 是单次，见 `packages/coding-agent/src/core/resource-loader.ts` 的 `loadModulesOnce`），技术路径是通的。

它仍然死在隔离上，而不是内存上：`SessionManager.inMemory()` 能解决不写盘，`session.dispose()` 能停自己的工具调用，但没有任何东西能停掉子会话里 `bash` 已经拉起的子进程树——现在这事靠 `killProcessTree` 杀整个进程组。同理，权限的替代只剩「共享父会话钩子」，那等于子代理里每个 `edit` / `bash` 都要回到父会话 UI 弹窗。

也就是说，「同进程」省的是 1 MiB/会话，付出的是 dev server 与子构建残留、父会话弹窗噪音，以及一颗 OOM 全体完蛋（现在子代理 OOM 只少一个 job，还能 `status`、重 spawn）。

## Consequences

- `pi-subagent-mini` 保持「子代理 = 独立 node 进程」。这条边界写在 [子进程启动方式](../../implemented/bug-fix/2026-10-16-subagent-child-process-launch.md)，本次不改。
- 后续真要做内存优化，优先级是：① 子进程模块表按需裁剪（省它自己那 29 MiB 独占），② 结构化回传（省 ~1 MiB/会话，外加协议简化），而不是整套同进程化。
- 两个操作后果，别再重新讨论一遍：
  - `MAX_CONCURRENT = 4` 是并发数限制，不看 RSS；写者串行只管写冲突。内存没有闸门。
  - 「N 个子代理 = N 倍内存」是错的。子进程的 `RssFile` 在机器上共享，真正翻倍的是独占部分（模块 + 堆），量级 10–40 MiB/个，不是 45–200 MiB/个。

## 测量方法（复现用）


这些数字来自一次性脚本，不是仓库测试；复核时按下面的形状重跑：

- 采 `/proc/<pid>/status` 的 `VmRSS` / `RssAnon` / `RssFile`，不要把 `ps` 的 RSS 相加。
- 进程起来等 0.8–1 秒再采，避开启动瞬态；用 `spawn` 而不是 `spawnSync`，否则父进程被阻塞时采不到正在跑的 pid。
- 会话状态样本要用真实不可压缩的内容（不同前缀的文本、工具输出）。V8 的字符串去重会让几百 MiB 的 `"x".repeat()` 只占 4 MiB，读数会骗人。
