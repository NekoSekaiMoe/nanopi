# Agent Note: write 的调用文本不做定稿后复用，流式高亮的开销也不在前缀重排

Status: rejected — `write` 定稿后新增的高亮行是 0，那层缓存只把拼字符串换成 O(n) 比较，且它换来的错误画面比省下的 CPU 更贵。见 shinytale/nanopi#652。

## Problem

`shinytale/nanopi#652` 提出给 `write` 补上 `bash` 那层调用文本复用（`rendered` / `renderedTheme` /
`renderedExpanded` / `renderedPath` / `renderedComplete`，命中就返回缓存字符串），理由是
`formatWriteCall` 在参数定稿后仍被反复调用、纯属白干；并把它当成
「前缀重排只在首次 exact 时做」的前置条件（[旧记录](2026-11-08-streaming-highlight-once-exact.md)）。

这个理由站不住，得先把结论钉住，否则那层缓存会被照着 issue 的描述实现一遍。

## Proposal

（被否决的原方案，保留以便对照。）

`WriteCallRenderComponent` 加 `rendered` / `renderedTheme` / `renderedExpanded` / `renderedPath` /
`renderedComplete` 五个字段，缓存键取「路径 + 展开态 + 主题 + 完整性 + `cache.exact`」，命中就返回
缓存字符串、不调 `formatWriteCall`；只在 `argsComplete` 且 `cache.exact` 为真时短路，命中时不调
`setText`。落地之后再按旧记录做「前缀重排只在首次 exact 时做」，即
```ts
const prefixCount =
    previous.exact ? Math.min(1, lines.length) : Math.min(STREAMING_FULL_HIGHLIGHT_PREFIX_LINES, lines.length);
```

## 为什么这层缓存是亏的

`updateStreamingHighlight`（`packages/coding-agent/src/core/tools/render-utils.ts:70`）的第一句：

```ts
if (reusable && previous.source === source && (previous.exact || !complete)) return previous;
```

参数定稿（`complete` 为真）且内容没变时，它原样返回上一次的 `StreamingHighlight`，
`formatWriteCall` 拿到的就是现成的 `cache.highlighted`，只做 `normalizeDisplayText`、
`split("\n")`、`slice(0, 10).join("\n")` 这类字符串拼接，**不再调用 `highlightCode`**。
`write` 的时序本来就和 `bash` 不同：bash 要防的是「定稿后每次 `updateResult` 都重新高亮一遍命令」，
write 在这一层已经短路，缺的那层省下的只是拼字符串。

拼字符串也不能靠比较省掉。缓存键如果按 issue 说的取「路径 + 展开态 + 主题 + 完整性 + `cache.exact`」，
`fileContent` 就不在键里——正文变了缓存照样命中，画面停在旧内容上；要正确只能把内容也纳入比较，
而 `updateArgs` 每帧换一个新 `args` 对象、`content` 每帧是新字符串，比较退化成 O(n) 的逐字符比对。
拿 O(n) 的比较换 O(n) 的拼接，收益是常数级的；`bash` 能这么做是因为它比的是短的 `command`。

正确性还有两个额外入口，`bash` 已经踩过：

- 主题。`updateStreamingHighlight` 复用的是引用相同的 `cache` 对象，缓存里带着旧主题的颜色；
  `bash` 把 `theme` 存成字段单独比，正是为了这件事（`renderers/bash.ts` 的 `component.theme === currentTheme`）。
- 语法懒加载。`cache.loads` 非空时画面是纯文本，要等语法加载完再重绘一次。`bash` 靠
  `component.rendered = undefined` + `context.invalidate()` 兜住；`write` 现在既不重绘也不清缓存，
  加了缓存而不补这条，第一次的纯文本画面会一直停着。

## 为什么流式期间的开销也不全在「前缀重排」

实测（400 行、逐帧 `updateArgs` 的 write 内容，`packages/coding-agent/test/streaming-highlight.test.ts` 同款的
`highlightedLines` 计数器，临时脚本跑完即删）：

- 流式 400 帧累计高亮 19624 行；
- `setArgsComplete()` 之后补 **0** 行，定稿后再打 10 帧 `updateResult` 也是 0 行；
- 画面上的每行都来自 `cache.highlighted`，折叠态只切出前 10 行。

19624 行里的大头是新增行那一遍（每行一次单行高亮），前缀重排只是每帧多出来的 ≤50 行。
也就是说，把前缀重排砍掉，省下的只是一部分，前提还得先补「新语言懒加载后重绘」，
否则跳过前缀会把近似画面留在终态——那正是旧记录否掉它的原因，而 issue 提的那层缓存并不改变这个前提。

顺带一个 correction：issue 说「`export-html/tool-renderer.ts` 里 `renderCall` 传的 `argsComplete` 恒为
`true`、`lastComponent` 跨折叠/展开共享」，前半句对（`core/export-html/tool-renderer.ts:90`），
后半句不对：跨折叠/展开共享 `lastComponent` 的是 `renderResult`（`renderedResultComponents`），
`renderCall` 用的是另一张 `renderedCallComponents`（`:61,112`），且只以 `expanded: false` 调一次
（`:112`）。它测不出缓存问题，只是一条独立的小回归，不必绑在这上面。

## Alternatives considered

### 实现缓存，但把 `content` 也纳入缓存键

最强理由：键里带上内容就不需要担心陈旧画面，配合 `exact` 也能保住 `streaming-highlight.test.ts`
那条「定稿后与新建组件逐行相等」的断言。

否决理由：内容在键里意味着每帧逐字符比较几百行文本，与它要省的 `formatWriteCall` 同阶。
省不出量级还会让 `cache.exact` 的失效路径更难读——参数定稿前画面本来就该重算。

### 直接按旧记录的第一条替代方案做前缀跳过

最强理由：实测流式期间前缀重排确实占了每帧的一部分，`exact` 的定义不需要额外字段。

否决理由：跳过之后，超过 50 行的跨行 token 内容停在近似画面上，而 `write` 定稿后不会再补一次全量。
旧记录已经因为这条否过一次，本 issue 提的缓存并不能改变它（缓存省的是拼字符串，不是高亮）。
