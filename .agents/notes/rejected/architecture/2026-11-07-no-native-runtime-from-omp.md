# Agent Note: 不把 ripgrep、shell、AST 链进进程（对照 oh-my-pi 那条路）

Status: rejected — 用户判断：omp 的原生层靠「单二进制免 fork/exec」+「6 平台分发 ~80k 行 Rust」换性能；nanopi 的产物是 10 MiB 级单文件、侧车按需下载，背不动也维护不起。三条候选（内嵌 shell、tree-sitter 摘要、in-band tool dialect）全不做。见 shinytale/nanopi#574。

## Problem

#574 对着 omp 的包结构问「能不能借鉴」。它最扎眼的做法是把别的 harness 靠 fork/exec 解决的活链进进程：

- **内嵌 bash 5.3 + in-process coreutils。** `grep`、`fd`、`sed`、`jq` 都不落盘，`pi-shell` 一个 crate
  就 38,000 行；README 正文说 58 个内置命令，crate 表说 67 个（它自己两处不一致）。
- **`read` 用 tree-sitter 做结构化摘要。** `pi-ast` 2,900 行、50+ 语言语法，`read` 只回选中块。
- **按模型族切换 in-band tool-call 线上格式。** `docs/toolconv/` 12 篇，DeepSeek 一支就 480 行，
  连标记符都必须用 `｜`(U+FF5C) 和 `▁`(U+2581)，换成 ASCII 就直接解析不出来。

nanopi 这三处的现状正好相反：

- `grep` 是 `ensureTool("rg")` 之后 spawn rg（`packages/coding-agent/src/core/tools/grep.ts:185`），
  `find` 是 `ensureTool("fd")`（`packages/coding-agent/src/core/tools/find.ts:242`），缺了就下载
  （`packages/coding-agent/src/utils/tools-manager.ts:349`）；拿不到二进制时降级到纯 JS 的
  `core/tools/fallback-walker.ts`（见 [grep/find 降级](../../implemented/bug-fix/2026-11-07-grep-find-fallback-without-rg-fd.md)）。
- 没有 tree-sitter：`pnpm-lock.yaml` 里零匹配，代码摘要能力只有 `pi-lsp-mini` 的 LSP。
- 只走结构化 `tool_calls`（`packages/ai/src/api/openai-completions.ts:647` 解析 delta，`:1376` 组装）。

所以「要不要学」是真问题。答案是三处都不学，但否的理由各不相同，各自记在这里。

## Proposal

三条候选全部不做：

1. **不引 Rust 原生层**，`grep`/`find` 继续走外部二进制 + 纯 JS 降级。「断网/无预装就报废」这个
   缺口已经用 `fallback-walker` 补掉了，正好证明它不需要 Rust 就能修
   （[grep/find 降级](../../implemented/bug-fix/2026-11-07-grep-find-fallback-without-rg-fd.md)）。
2. **不引 tree-sitter**，`read` 维持行号截断 + `offset=N to continue` 的续读提示
   （`packages/coding-agent/src/core/tools/read.ts:226-235`）。
3. **不引 in-band tool-call dialect**，只发结构化 `tool_calls`。

## 为什么不引 Rust 原生层

omp 的收益成立在两个前提上，nanopi 一个都没有。

**前提一：分发一个能装下 80k 行 Rust 的二进制。** omp 按 `linux/darwin/win32 × x64/arm64` 六平台分发，
x64 还要双份（AVX2 与 baseline）。nanopi 的 `full` 产物是 10,213,090 字节、`base` 6.7 MiB、
`minimal` 2.7 MiB（[sidecars 不再内嵌](../../implemented/process/2026-11-06-sidecars-download-in-full.md)），
而且体积预算是被单独管着的（[trimmed flavor 预算](../../implemented/process/2026-10-22-trimmed-flavor-size-budget.md)）。
原生层一进来，「每多一个平台就多一份产物」和「每个产物都要装 6 份架构」这两笔账同时出现，
而省下的只是一次 `spawn` 的几毫秒。

**前提二：调用密到 fork/exec 值得优化。** nanopi 一次会话里 `grep`/`find` 是几十次量级，不是 omp 那种
内嵌 shell 逐条命令都走进程内 dispatch 的量级。同一时段已有的侧车机制（TUI `.node` 预编译、photon wasm，
`packages/coding-agent/src/utils/sidecars.ts`）连 0.9 MiB 都要权衡——`full` 正因为这 0.9 MiB 把内嵌关掉了。
一个 80k 行、六平台、双 AVX2 的 addon 放在这套预算里没有讨论空间。

顺带记住一条反面证据：omp 的 `pi-builtins` 里 67 个命令是从 coreutils 一族移植来的，
文件自己就在说「第三方代码有自己的 LICENSE」（README 第 698 行附近）。这不是白拿的代码量。

## 为什么不引 tree-sitter

`read` 的结构化摘要（省略中间声明、只留选中块）收益是 token，前置条件是「你得先有一棵语法树」。
nanopi 要做得先引一整套 grammar 分发（omp 是 50+ 语言、编译进同一个 addon），再为多语言各写一套
选择规则。而 `read` 现在的预算控制是行号 + 字节截断 + 续读提示，模型不需要理解语法就能接着读。

换句话说：这是「为一个少给几行的优化引一整棵语法树」。真出现「模型反复读大文件读不完」的证据再说。

## 为什么不引 in-band tool-call dialect

`docs/toolconv/deepseek.md` 读下来是血泪史，反而是最该照抄它结论的一篇：全角 `｜`(U+FF5C) 和
`▁`(U+2581) 不能替换成 ASCII、V3-0324/R1-0528 与 V3.1 两套语法、DSML 又来第三套、
且没有 `tool_call_id` 只能按位置匹配工具调用与结果。nanopi 只发结构化 `tool_calls` 是对的，
兼容性问题交给 `packages/ai/src/providers/compat-schema.ts`（634 行）那一层按 provider 修，
而不是在每个模型族上重造一套线上格式。

## 不在这篇范围内、但已被单独否掉的

omp 的插件市场 / hooks / 记忆系统（含 SQLite 记忆引擎）对 nanopi 没有新信息，各有结论：

## Alternatives considered

### 只把 ripgrep 链进来，其余不引

最强理由：`grep` 是 nanopi 最热的搜索路径，也是离线降级最痛的一处，单独引 `grep-regex` + `grep-searcher`
（omp 的 `grep` 模块 3,280 行）比整套原生层便宜得多。

否决理由：省下的是 `spawn` 的固定开销，而这笔开销的绝对值在 nanopi 的调用密度下测不出来；
同时仍要付「按平台分发原生 addon」的全套成本，以及 Rust 工具链进 CI。而离线场景的正解已经落地成
纯 JS 回退（`ignore` 本来就在依赖里，`packages/coding-agent/src/core/skills.ts:2` 在用），
那条路不碰分发格式——降级路径与 rg 共享 ignore/glob/符号链接语义，只是慢一个数量级。

### 用 `read` 的 AST 摘要换掉续读提示

最强理由：对大文件确实是「少给几行」的直接收益，且 omp 有现成规则可抄。

否决理由：它和续读提示不是替代关系——语法树切块之后，模型仍然需要「剩下的在哪」的坐标。
收益只在「模型本可以不读那部分」时兑现，而这个前提没有证据。真要做，先量一次「读大文件占总 token 的比例」。

## Consequences

- `grep`/`find` 的离线/无预装降级是独立缺陷，已按纯 JS 回退修完。原生层这条路省不下它，
  也不该拿它当选 Rust 的理由。
- 原生层这条路以后被重提时，先看两条前提是否变化：产物预算是否放开到几十 MiB、调用密度是否高到
  `spawn` 可测。两条不变就别再讨论。
- `compat-schema.ts` 与 `docs/providers.md` 是 in-band dialect 的替代承载面，查漏去那儿查，
  不要往 wire 格式上重造。
