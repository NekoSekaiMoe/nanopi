# Agent Note: 评论去重的幂等 id（不做）

Status: rejected — 触发场景是「同一个 NPC 被连触发两次」，不是「发送重试」；nanopi 本体不发评论，这条落不到代码里，需求面太窄，不做。

## Problem

同一份状态被回了两遍时，读者无法分辨哪条是新的。真实触发是两个，都发生在 NPC 外壳而不是 nanopi 里：

- 人在评论里补了一句话，或构建重跑，agent 对着同一份状态又回了一遍
- 一次发送失败后重试，而远端其实已经收到

第二种在 dsh 的 `docs/008-cookbook.md:177` 被写成「`message.id` 作幂等键」。它的理由值得抄的只有
一句：**不是「重试会重复」，是「重试时远端可能已经收到了」**——失败和成功之间有个客户端分辨不了
的窗口。

## Proposal（被否决的原方案，保留以便对照）

最小形态是 `issue 号 + 本轮序号 + 内容哈希`，发之前 grep 最近 N 条评论，同哈希就跳过，不建中心表。
dsh 的另外两半不抄：Outbox 严格按入队顺序发（评论区的顺序天生由发表时间决定，客户端定序是假的），
`hookq --key` / GitHub 隐藏标记 / 飞书幂等键都是它自己渠道的实现细节。

## Alternatives considered

### 挂在别处做

这条单独立不了项：`AGENTS.md` 只规定了「写到临时文件再 `--body-file`」，没有任何发送重试层可以挂幂等
键。要做只能做成 NPC 外壳的约定，和 nanopi 的代码不同批。

### 只做「连触发两次」那一半

去重靠「最近 N 条评论同哈希」，但 NPC 每次的正文几乎不可能字节相同，真要判重得先定义「同结论」，
那是语义判断，不是哈希。哈希只能拦住重试，而重试恰好是这里最不常见的那半。
